# Runtime configuration — `public/config/` (the single source of truth)

These four JSON files drive the **Basic Information** and **Task Summary** dropdowns.
**`public/config/` is the ONE place to edit them.** There is intentionally no second copy:

- **Dev** (`npm run dev:all`) — Vite serves these files at `/config/*.json`, and the in-app
  Config → Team editor writes them here.
- **Build** — `vite build` copies `public/config/` verbatim into `dist/config/` (the image defaults).
- **Prod** — the container auto-seeds a fresh host volume from those baked defaults on first boot
  (see *Production* below); after that the volume is the live source of truth.

> **Never hand-edit `dist/config/`** — it is gitignored build output, regenerated by `vite build` and
> shadowed by the prod volume. There is no longer a `deploy/config/` copy.

## The five files

| File | Controls | Shape |
|------|----------|-------|
| `projects.json` | Project/Team dropdown in Basic Information | `ProjectConfig[]` |
| `team-members.json` | Assignee list (filtered by selected project) | `Record<projectKey, TeamMember[]>` |
| `summary-options.json` | Vehicles, Products, Layers in Task Summary | `{ vehicles, products, layers }` (all `string[]`) |
| `components.json` | Component list in Task Summary — **scoped per Agile Team** | `Record<projectKey, string[]>` |
| `project-matrix.json` | Config → Project product-coding matrix (edit-gated by the `projects` code) | `ProjectMatrixRow[]` (产品线 + 6 code fields; 综合编码 is derived) |

### Key-match invariant

The keys in `team-members.json` and `components.json` **must** match `projects.json[].key`:

```
projects.json has         → { key: "HW", ... }
team-members.json needs   → { "HW": [...] }
components.json needs      → { "HW": [...] }
```

A project key present in `projects.json` but missing from `components.json` shows an empty component list
(still selectable, just no datalist suggestions).

## Schemas

### `projects.json`
```json
[ { "name": "IDC_PDHW", "key": "HW", "teamName": "Hardware Team" } ]
```

### `team-members.json`
```json
{ "HW": [ { "id": "GW00012345", "name": "Alice Chen", "role": "HW Designer" } ] }
```
`role` is optional. `id` is the JIRA assignee identifier; `name` is what the user sees.

### `summary-options.json`
```json
{
  "vehicles": ["Platform", "GWM_DE09", "GWM_EC15"],
  "products": ["EPS", "IBC", "EMB"],
  "layers": ["SYS", "SW", "APP", "HW", "ME", "VV", "Devops", "PMO"]
}
```

### `components.json`
```json
{ "HW": ["PIU", "MCU"], "DKKF": ["MCAL", "EcuM"], "SWCD": ["Dcm", "Nm", "Xcp", "CanTp"] }
```

## Adding a team or a layer

- **New team**: add it to `projects.json` (`{ name, key, teamName }`) AND add the same `key` to
  `team-members.json` and `components.json` (key-match invariant). Optionally add a per-team edit code to
  `team-codes.json` (see *Production*) — the `"*"` master code already unlocks any team.
- **New layer** (e.g. `PMO`): add the string to `summary-options.json` `layers`, drop bilingual coach-skill
  files `src/config/skills/coach-skill-task-<layer>-{en,zh}.md`, and register them in
  `src/config/skills/index.ts` (`TASK_SKILL_MAP`). A missing map entry silently falls back to the SW skill.

## Validation & fallbacks

On startup the app fetches each file, validates its shape, and falls back to baked-in defaults
(`src/config/projects.ts`, `src/config/constants.ts`) if anything is wrong. The defaults are a safety net
only — edit the JSON here, not the source. Check the browser console:

```
[runtime-config] loaded: projects=runtime, team=runtime, summary=runtime, components=runtime
[runtime-config] /config/components.json: HTTP 404 — using fallback
[runtime-config] /config/components.json: invalid shape (...) — using fallback
```

## Production (Docker)

Compose mounts two host dirs (see `deploy/docker-compose.yml`):

| Host path | Container | Holds |
|-----------|-----------|-------|
| `/usr/local/smart_agent/data` | `/app/dist/config` | the runtime config files (web-served) |
| `/usr/local/smart_agent/quality-db` | `/app/data` | SQLite DB **and** `team-codes.json` (secret, NOT web-served) |

> ⚠️ **Never put `team-codes.json` under `public/` or `dist/config`** — those are web-served, so the edit
> codes would be fetchable at `/config/team-codes.json`. Codes live ONLY in the data volume (alongside the
> DB), read via `CODES_PATH`. The `projects` key gates the Config → Project matrix editor.

- **First-boot auto-seed:** the entrypoint (`deploy/docker-entrypoint.sh`) copies any missing config file
  from the image's baked defaults (`/app/config-defaults`, built from `public/config`) into the volume.
  No manual seeding step. It only fills gaps, so ops/editor edits are never overwritten.
- **Editing in prod:** use the in-app Config → Team editor, or edit the mounted file directly:
  ```bash
  vi /usr/local/smart_agent/data/components.json
  docker compose restart smart-agent      # then users hard-refresh (Ctrl+Shift+R)
  ```
  Each page load cache-busts `/config/*.json` with `?v=<timestamp>`.
- **Decoupling:** once a prod volume is seeded, changing `public/config` + rebuilding the image does NOT
  update prod (the volume is the live truth). Push such changes via the in-app editor or the host file.
- **Per-team edit codes:** place `team-codes.json` at `/usr/local/smart_agent/quality-db/team-codes.json`
  (`deploy/team-codes.sample.json` shows the shape; `"*"` is an ops master code). Read fresh per request —
  no restart needed to rotate codes.
