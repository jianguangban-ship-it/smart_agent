● Time field recommendation: Event timestamp (ticket.timestamp → event_time)

  It's the better and more robust choice, for four reasons:

  1. It's the domain event time — "when n8n produced this quality verdict."
  That's exactly the axis a quality-over-time review should measure. updatedAt
  is CURRENT_TIMESTAMP set on every DB write — an implementation detail, not a
  business fact.
  2. It's already indexed (idx_tickets_event_time ON tickets (event_time DESC)),
   so server-side WHERE event_time BETWEEN ? AND ? range queries are efficient
  with zero schema changes.
  3. Retro stability — with updatedAt, any unrelated re-post would yank a ticket
   into a different week/sprint bucket. event_time keeps a verdict anchored to
  when it actually happened.
  4. Future-proof — it cleanly separates "when assessed" from DB mechanics,
  leaving room to later add other time axes (e.g. JIRA-created date) without
  conflating them.

  One caveat I need to flag for the "trend" part

  The DB keeps one row per issue_key (upsert overwrites; event_time becomes the
  latest check's time). So a trend can show "distribution of each ticket's 
  latest verdict, bucketed by when that verdict happened" — but it cannot
  reconstruct "what did Sprint S2's quality look like back then" if tickets were
   re-checked afterward, nor show a single ticket's quality history. For most
  cases (a ticket checked ~once per sprint) this is fine. A fully robust
  historical trend would need an append-only events table — a larger change.

     Context

     Why this change: View mode's JIRA Quality Grid (QualityGridPanel.vue +
     useQualityGrid.ts)
     currently fetches all tickets from GET /api/tickets and filters only by
     team / status /
     search text. There is no time dimension. R&D leads and scrum masters need
     to review the
     quality of JIRA tickets over a timing phase — e.g. "this sprint", "this
     PI", "last 7 days",
     "last month", or a custom date range — and compare teams within that phase
     (e.g. for a sprint
     retro).

     Outcome: In View mode the user picks a timing phase (calendar or
     sprint-aligned, plus a
     custom range). The grid narrows to that phase server-side, and two new
     read-only widgets appear:
     a summary strip (period totals + A/B/C/D/格式异常/未知 distribution) and a
     per-team trend
     matrix (teams × sub-period buckets, each cell a colored stacked bar).

     Decisions locked with the user:
     - Output = grid + summary + trend.
     - Time field = event_time (n8n verdict time): indexed
     (idx_tickets_event_time),
     domain-meaningful, retro-stable (immune to unrelated DB re-writes).
     - Periods = both calendar (Last 7 days / Last 30 days / Custom) and
     sprint-aligned
     (Current Sprint / Last Sprint / Current PI), reusing the existing sprint
     model.
     - Filtering site = server-side date range; team/status/search stay
     client-side as today.
     - Trend = snapshot buckets, no schema change (each ticket's latest verdict
     bucketed by
     event_time). Accepted limitation: cannot reconstruct historical sprint
     quality if a ticket
     was re-checked after the sprint, nor show a single ticket's quality
     history. A future
     append-only events table is the upgrade path (out of scope here).
     - Breakdown = per-team within the period.

  It's inherited convention, not a deliberate choice for View mode. Explore and

  objecting to.

  demote/remove the "JIRA Quality Grid" widget header (the app already has a
  header that can carry the mode title).

● Good — these two questions get at the real decision. Direct answers:

  1. Does flattening trade off UX?

  It depends entirely on how it's flattened. There are two versions:

  Naive flatten (truly edge-to-edge, header removed) — yes, this does cost UX:
  - On wide/ultrawide monitors the table and trend matrix stretch full viewport
  width → long eye-travel, harder row scanning (optimal scan width is bounded).
  - The "JIRA Quality Grid" header currently houses the refresh button + ticket 
  count — remove the header naively and those controls lose their home.
  - The card border/shadow does one useful thing: it signals "this is a
  contained data surface," which aids orientation.

  Disciplined flatten (remove card chrome, but keep a max-width content 
  container + a slim toolbar row) — essentially no UX downside, only gains:
  - Reclaims the redundant frame padding + min-height → data sits higher, more
  rows visible without scrolling.
  - Kills the "frame-within-the-window" confusion.
  - Keeps refresh/count/period controls in a lightweight toolbar (no widget-card
   look).

  So the honest answer: the recommended flatten is the disciplined one, which is
   effectively the "Hybrid" I listed — that's the version with no real UX
  trade-off. The pure full-bleed version trades off scannability and control
  placement.

  2. Is this good for future data-visualization upgrades?

  Yes — strongly, and this is the more important reason than aesthetics.

  The current structure is one big card containing everything. The standard
  dashboard pattern for data viz is the opposite: a flat page background with 
  multiple light cards/sections (a KPI strip, a trend chart, a distribution
  chart, the matrix, the table). If you later add charts (quality trend lines,
  burndown, heatmap, per-PI comparison), you'd be nesting cards inside a card —
  frame-within-frame-within-frame, fighting the viewport for width.

  Flattening now is a prerequisite/enabler for that: it turns View mode into a
  real dashboard canvas where each future viz widget is its own self-contained
  card on a flat surface, arranged in a responsive CSS grid. Doing it now (with
  ~4 small components) is far cheaper than retrofitting it after 6 charts are
  wedged into the monolithic card.

  One caveat so I'm not overselling: flattening is necessary but not sufficient.
   The full viz upgrade still needs a deliberate section/grid layout —
  flattening just removes the structural blocker and the redundant chrome.

  My refined recommendation

  Go with the disciplined flatten: remove the card
  border/shadow/radius/min-height and the widget-style title block, keep a 
  max-width container (so tables don't sprawl on wide screens) and a slim 
  toolbar for period selector + refresh + count. This is the "no UX trade-off,
  future-viz-ready" option.

● I now have the full picture. The crux: useLLM() is instantiated once in
  App.vue (line 352), and coach is a single createStreamFlow instance with one
  messages array and one AbortController. Task and Explore today share that one
  pipeline — only the system prompt differs (coachSkillEnabled). That single
  shared flow is exactly why your scenario breaks.

  Approaches

  A — Two parallel channels via the existing createStreamFlow factory 
  (recommended). Instantiate taskCoach and exploreCoach from the factory that
  already exists. Each gets its own messages, isLoading, wasCancelled/hadError,
  backoff timer, and its own AbortController — so two requests stream
  concurrently with zero new streaming infra (the factory was already hardened
  for concurrent 429s). Task handlers route to taskCoach; the new Explore
  composer routes to exploreCoach. Lowest risk, reuses proven code.

  B — One flow holding a Map<channel, conversation>. More generic (N channels)
  but a deep rewrite of createStreamFlow and every call site for two fixed
  channels — over-engineering (YAGNI).

  C — Snapshot/restore conversation on mode switch. Single flow, swap messages
  in/out. Cannot stream both concurrently (one AbortController) → fails your
  chosen requirement. Rejected.

  I recommend A.

  Proposed design

  Architecture. Split the single coach flow into taskCoach and exploreCoach
  (both chatMode:true). taskCoach.getSystemPrompt keeps the current skill/trace
  logic; exploreCoach.getSystemPrompt always returns getResponseFormat() (free
  chat) — no appMode coupling, so each is self-contained and concurrency-safe.
  useLLM() stays an app-singleton, so an in-flight stream keeps running and 
  updating its messages array even while its panel is unmounted — switching
  modes never interrupts it.

  Components. Task mode: unchanged — existing CoachPanel + TaskForm, now bound
  to taskCoach. Explore mode: a new single-column chat surface (full-width
  conversation reusing ChatBubble, composer docked at the bottom) bound to
  exploreCoach, replacing the TaskForm-as-input split. Other modes/layouts
  untouched.

  Data flow & input decoupling. The Explore composer gets its own input state, 
  decoupled from form.description — critical for your use case: asking an
  Explore question mid-task must not touch the half-written task description.
  Explore send → free-chat payload (description = composer text) →
  requestExploreCoach. Task "Coach" button → structured payload →
  requestTaskCoach, exactly as today.

     }
